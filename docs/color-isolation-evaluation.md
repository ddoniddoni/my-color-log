# 색 강조 D/E단계 — 평가와 개선 기록

## 일상 팔레트의 갈색·베이지 지원 (2026-10-26)

관련 요구사항은 FR-MISSION-003, FR-PHOTO-002다. [일상 8색 + 특별 2색](color-reveal.md) 중 새로 추가한 갈색·베이지는 hue만 비교하면 주황·노랑까지 함께 남는다. 기존 Skia 경로에서 색상군별 밝기·채도 조건을 추가했다. 미리보기와 저장은 같은 셰이더와 uniforms를 사용하며, 색상 판정으로 사진 저장을 막지 않는다.

- 갈색: 따뜻한 hue 범위에 밝기 상한을 함께 적용하여 나무·짙은 갈색을 살리고 밝은 주황·노랑·베이지를 억제한다.
- 베이지: 따뜻한 hue, 낮은 채도 범위와 밝기 하한을 함께 사용한다. 회색·흰색·짙은 갈색·선명한 노랑/주황을 구분한다.
- 두 색의 채도 강조 배수는 1.10으로 절제한다. 다른 목표색은 기존 1.35를 유지하고, 빨강/분홍 경계 수정도 유지한다. 특정 slug를 검사하지 않으므로 과거 목표색도 기존 HEX로 처리한다.

실제 SkSL 픽셀 회귀 2개와 sRGB/Display P3 동등 입력을 추가했다. 총 26개 shader 테스트에서 갈색의 밝고 어두운 표본, 베이지 종이/천 표본, 두 색의 혼동색·무채색 억제와 기존 색상군 동작을 확인했다. 공개 Coffee 사진(CC0)을 두 목표색으로 추가 렌더링하여 시각적으로 확인했으며, 이는 새 정답 마스크 기반 정확도 측정이 아니다. 조명에 따라 짙은 주황과 갈색, 밝은 나무와 베이지가 겹치고 가장자리 선택이 고르지 않은 한계가 남는다. 아래 과거 공개 사진 점수나 기존 `scripts/color-isolation/palette.json`의 10색 평가를 새 일상 10색 전체의 검증 점수로 해석하면 안 된다.

`npm run check` 통과: 타입·린트, Jest 85 suites / 403 tests, 평가 도구 10 tests, Node 설정 계약 21 tests. React Doctor 변경 범위는 새 진단 없음(88/100). 이 점수는 변경 범위 검사이며 아래의 전체 코드 검사 점수와 직접 비교하지 않는다. DB 계약과 서버 적용은 [공유 Supabase 안내](shared-supabase.md#팔레트-업데이트)에 기록한다. 새 의존성·사진 저장 형식 변경은 없으며 네이티브 빌드/실기기 확인은 실행하지 않았다. 이미 효과를 적용해 저장한 사진은 재처리하지 않는다. 최신 JS로 새 촬영을 진행하여 실제 iPhone/Android의 조명·반사·저장 결과를 확인해야 한다.

## 빨강·분홍 오인식 후속 수정 (2026-10-26)

관련 요구사항은 FR-PHOTO-002다. 사용자 화면에서 토마토 레드 미션인데 분홍빛 마우스가 강조되는 현상을 확인했다. 첨부 화면은 이미 효과가 적용된 결과이므로 원본 RGB나 촬영 조명을 복원했다고 주장하지 않는다. 아래 재현은 대표 분홍색 합성 표본과 기존 공개 사진 평가를 사용했다.

- 원인: 빨강의 대칭적인 hue 거리 허용 범위에 자홍·분홍이 포함됐다. 선택 마스크가 부분적으로 남아도 기존 채도 강조 때문에 선명하게 보였다. 예를 들어 RGB `(210, 50, 95)`는 선택 마스크 0.698, 출력 `(168, 22, 63)`이었다. `(220, 40, 76)`은 마스크 0.984로 거의 전부 강조됐다.
- 수정: 빨강 목표(hue 355~360° 또는 0~12°)의 차가운 색 방향에만 추가 경계를 둔다. 일반 픽셀은 350~356°에서 부드럽게 사라지며, 기존 색 일치도를 곱해 다른 색을 새로 선택하지 않는다. 채도가 높은 짙은 빨강은 작은 추가 범위(344~348°)를 허용한다. 이 확장은 V 0.50~0.65에서 사라지고 S 0.82~0.90에서 활성화되며, 기존 암부 잡음 억제는 계속 적용한다. 와인·핑크 목표의 기존 판별은 유지한다.
- 단순히 hue만 좁힌 시안은 NASA 사진의 붉은 깃발을 누락해 채택하지 않았다. 최종 구현에서는 해당 주석 영역의 TP 493 / FN 0을 유지했다. 이 장면의 기존 주황 의상 오검출(FP 1,434)은 해결 범위에 포함하지 않았으며 남아 있다.
- 대표 분홍 표본 5개 `(210,50,95)`, `(170,75,105)`, `(115,45,65)`, `(230,140,165)`, `(220,40,76)`의 토마토 레드 선택 마스크는 모두 0이 됐다. 실제 핑크 미션에서는 같은 표본을 계속 강조한다. 빨강의 밝은 부분·그림자·0° 양쪽 경계와 sRGB/Display P3 동등 입력, 투명도 검증도 통과했다.
- UI의 `발견한 색`은 사진 분석 결과가 아니라 전달받은 미션 이름이었다. 검출 성공으로 오해하지 않도록 `오늘의 색`으로 바꿨다.

기존 공개 사진 6장·11개 장면/목표 조합과 합성 평가를 수정 전후 같은 입력으로 다시 실행했다. 0.5 검출 문턱에서 기존 모든 평가 행의 TP/FP/FN/TN은 동일했다. 이 수치는 0.5 미만으로 남는 색의 시각적 오검출을 놓칠 수 있으므로, 이번 회귀 테스트는 최종 렌더링 RGB의 채도도 검사한다. 대표 로즈 핑크의 빨강 마스크는 0.404→0, 와인은 0.075→0이다. 최종 셰이더·uniforms는 미리보기와 저장에서 함께 사용한다.

검증: 신규 회귀 7개를 포함한 실제 SkSL 픽셀 테스트 24개, `npm run check` 통과(타입·린트, Jest 85 suites / 399 tests, 색 평가 도구 10 tests, 설정 계약 21 tests). React Doctor 변경 범위의 새 진단은 없었고, 같은 도구 버전으로 기준 HEAD와 현재 코드를 전체 비교해 점수 83/100 및 기존 진단 25개가 동일함을 확인했다. `test:build`는 Node 설정 계약이며 네이티브 앱 빌드는 실행하지 않았다. 공개 사진 비교 산출물은 `/tmp/mycolorlog-red-pink-before/`, `/tmp/mycolorlog-red-pink-after/`에 있다. 기존 주석을 바꾸거나 출시 판정 기준을 낮추지 않았고 `releaseGate.status = not-evaluated`를 유지했다.

네이티브 의존성·DB·사진 저장 형식 변경은 없다. 이전에 효과를 적용해 저장한 사진을 다시 처리하지 않는다. 기존 개발 앱에서 최신 JS를 새로고침한 뒤 새 촬영으로 확인할 수 있다. 마우스 원본 및 실제 iPhone/Android의 조명·화면·저장 결과 검증은 남아 있으며, 같은 RGB로 촬영된 서로 다른 물체의 실제 색을 이 픽셀 필터만으로 구별할 수는 없다.

## 결정

기존 Skia 렌더링 경로를 유지하고, E에서는 **색상군별 hue 범위·채도/명도 허용 범위**를 개선하는 후보를 구현한다. 이번 HSV·OKLCH 실험의 고정 파라미터를 앱에 그대로 적용하지 않는다. 단일 Oklab 거리로 바꾸는 안도 채택하지 않는다. 세부 이유는 아래 실측 결과에 있다.

OpenCV 도입이 필요한 증거는 아직 없다. 현재 확인한 문제는 잘못 남긴 색과 넓게 누락한 색 영역이며, 마스크 잡음 정리만으로 해결되지 않는다. 후처리와 새 네이티브 라이브러리는 이득을 입증한 뒤 검토한다. 이번 단계의 새 런타임/개발 의존성은 0개다.

사용자는 공개 사진으로 우선 진행하고 자신의 실제 촬영 사진 확인은 마지막 기기 QA에서 하기로 했다. 사진은 로컬에서만 처리했다. Supabase의 사용자 사진을 조회하거나 외부 분석 서비스로 전송하지 않았다.

## 재현한 원인

D의 기존 `colorIsolation.ts`는 각 픽셀과 목표색을 `(rgb - min) / (max - min)`으로 정규화한 뒤 거리를 비교한다. 색이 있는지 판단하는 최소 채도·밝기 조건은 있지만, 목표와 픽셀 사이의 명도·채도 차이는 비교에서 사라진다.

- 와인 `#8B1E4B`를 목표로 하면 로즈 핑크 `#EC407A`도 완전히 살아난다. 실제 baseline SkSL을 CanvasKit으로 실행해 재현했다.
- 와인색 잎 사진에서는 밝은 핑크가 남고 어두운 잎의 상당 부분이 빠졌다. 부분 주석 영역 recall은 0.185였다. 이는 실제 사용자가 찍었던 사진의 재현과는 구분한다.
- 자연광 보라 꽃은 기존 방식도 부분 영역 recall 0.995였다. “보라색이면 항상 실패한다”는 가설은 지지하지 않는다.
- 잎의 노란 기운과 옅은 하늘색처럼 대표 HEX에서 벗어난 색이 어려웠다. 모든 색의 채도 하한을 높이면 하늘을 잃고, hue 범위를 한꺼번에 넓히면 피부·붉은 갈색도 남는다.
- 알파 해제/복원과 `layout(color)`는 기존 코드에 이미 있다. 이번 결과로 Display P3 처리 오류나 미리보기/저장 불일치까지 재현했다고 주장하지 않는다.

## 평가 자료와 방법

**공개 사진 6장, 장면-목표색 조합 11개**, 합성 표본 10색 × 20개 픽셀을 사용했다. 같은 사진의 여러 목표색은 독립 사진으로 세지 않는다. 합성 표본에는 기준색, 그림자, 따뜻한 색 편향, 밝은 변형, 다른 팔레트색, 흰색/회색/암부가 있다. 와인의 밝은 변형처럼 핑크와 의미가 겹치는 표본 1개는 평가에서 제외했다.

원본을 시각적으로 확인한 에이전트가 명확한 내부 영역을 사각형으로 표시했다. **사람이 검수한 전체 정답 마스크가 아니다.** 표시하지 않은 곳과 애매한 색 경계는 무시한다. Coffee의 목표색 부재 두 경우만 전체 프레임을 음성으로 평가한다. 피부는 이 한 장면만 포함하므로 다양한 피부색 검증을 대신하지 않는다.

모든 후보는 같은 sRGB 8-bit 입력과 동일한 영역을 사용한다. CanvasKit 0.41.0 CPU surface에서 실제 SkSL을 실행했다. EXIF 방향을 반영해 긴 변 최대 640px로 디코딩/축소한 뒤 픽셀만 재인코딩한다. 원본 다운로드는 임시 캐시에만 있고, 생성된 보고서 이미지는 원본 EXIF/위치를 복사하지 않는다. 이는 앱의 1600px 저장 해상도·GPU 성능·JPEG 85 품질 검증을 대신하지 않는다.

baseline은 `cb63022`의 셰이더를 `baseline.sksl`로 고정했고, D 당시 제품 코드와 동일함을 확인했다. 이후 제품 코드가 바뀌어도 기준값을 덮어쓰지 않는다. 모든 후보에서 마지막 합성 출력만 마스크로 교체해 분류 결과를 읽으며, 실제 강조 이미지도 별도로 렌더링한다. 배경 밝기 0.82·채도 강조 1.35는 후보 모두 동일하다.

- 마스크 `>= 0.5`를 검출로 고정한다. 8-bit 출력에서는 128 이상이다.
- precision = TP/(TP+FP), recall = TP/(TP+FN), ROI IoU = TP/(TP+FP+FN).
- 검출이 없는 양성 장면의 precision은 0으로 집계한다. 목표색 없는 장면은 precision/recall/IoU 평균에서 제외하고 잘못 남긴 면적 비율 FP/(FP+TN)을 별도로 기록한다.
- 표의 평균은 **주석 있는 장면-목표 조합의 macro 평균**이다. 사진 전체의 10색 정확도나 전체 픽셀 accuracy가 아니다.
- 같은 장면은 development/validation 양쪽에 들어가지 않도록 도구가 검사한다. 후보 파라미터와 주석을 정한 후 validation 결과를 열었고 결과에 맞춰 수정하지 않았다. 이제 결과가 공개되었으므로 E에서 이 장면을 참고해 조정할 경우 새 최종 holdout이 필요하다.

| Color.js | 색차 계산을 검산할 개발 도구 후보. **설치하지 않음** | 사진 전체 JS 픽셀 처리 경로로 사용하지 않음 |

[Skia RuntimeShader](https://wcandillon.github.io/react-native-skia/v2/docs/image-filters/runtime-shader/)는 기존 이미지 필터 경로를 유지할 수 있고 픽셀 밀도 주의사항이 있다. [SkSL 문서](https://skia.org/docs/user/sksl/)는 작업 색 공간과 premultiplied alpha를 설명한다. 실험의 sRGB 수동 선형화를 앱에 복사하지 말고, E에서는 `toLinearSrgb`를 포함한 작업 색 공간 처리를 확인한다.

[Oklab 원저자 자료](https://bottosson.github.io/posts/oklab/)의 linear sRGB 변환식을 사용했다. 이번 후보는 OKLCH hue/명도/채도 조건이며 ΔE2000 비교가 아니다. [Color.js 색차 문서](https://colorjs.io/docs/color-difference)의 여러 색차 스케일과 혼용하지 않는다.

[OpenCV HSV inRange](https://docs.opencv.org/4.x/da/d97/tutorial_threshold_inRange.html)는 범위 판별의 참고 자료다. 이 실험의 부동소수 HSV soft mask를 OpenCV의 정수 HSV 출력과 동일하다고 주장하지 않는다. [형태 연산 문서](https://docs.opencv.org/4.x/d9/d61/tutorial_py_morphological_ops.html)의 opening은 작은 영역을 제거할 수 있으므로 얇은 줄기·작은 물체 손실을 따로 확인해야 한다.

호환성/라이선스 조사(2026-10-22): 현재 앱은 Expo 57 / RN 0.86.3 / Skia 2.6.2이며 Skia는 [MIT](https://raw.githubusercontent.com/Shopify/react-native-skia/v2.6.2/LICENSE.md)다. Fast OpenCV 저장소의 [현재 package.json](https://raw.githubusercontent.com/lukaszkurantdev/react-native-fast-opencv/main/package.json)은 1.0.1, 개발 RN 0.85.0, peer RN `*`를 표시한다. 이것이 우리 버전의 빌드 호환 증거는 아니다. 래퍼는 [MIT](https://raw.githubusercontent.com/lukaszkurantdev/react-native-fast-opencv/main/LICENSE), OpenCV 4.5 이상은 [Apache 2.0](https://opencv.org/license/), Color.js는 [MIT](https://raw.githubusercontent.com/color-js/color.js/main/LICENSE)다. ## E 구현 기준과 남은 검증

초기 채택 기준을 낮추지 않는다. 정식 검증은 40장 이상의 독립된 장면과 사람이 검수한 전체 마스크로 macro IoU +0.05 이상, 색상군별 precision/recall 하락 0.03 이내, 보라·와인 누락 감소, 목표색 없는 장면의 오검출 면적 비율 악화 없음을 확인한다. 현재 도구는 부족한 자료를 성공으로 표시하지 않고 `releaseGate.status = not-evaluated`를 출력한다. 이번 결과로 어느 후보도 출시 승인하지 않는다.

E의 우선 작업:

1. 밝은 핑크와 어두운 와인의 구별에 명도 정보를 제한적으로 반영한다. 밝은 반사 부분·그림자까지 잘라내는 전역 상한은 피하고 실패 장면을 함께 검증한다.
2. 보라·와인·초록·연한 파랑/민트의 hue 폭과 저채도 허용 범위를 분리한다. 유효한 과거 미션색에도 동작하며 특정 활성 slug만 지원하는 로직은 만들지 않는다.
3. 흰색/회색/암부 억제를 유지하고, hue 확대 후 피부·목재·붉은 갈색 오검출을 다시 확인한다. RGB만 같은 두 영역은 사물 의미로 구분할 수 없다는 한계를 명시한다.
4. 분류 마스크와 배경/채도 연출을 분리해 미리보기·저장이 같은 파라미터를 사용하게 한다. 원본 저장 선택, 효과 중복 방지, 큐/실패 복구는 유지한다.
5. 40장 자료를 확장하고 독립 holdout과 사람 마스크 검수를 완료한 후 최종 판정한다. 이 파일럿에는 10색 모두의 독립 validation 사진, 다양한 피부색·실내 조명·기기 P3 입력이 없다.

F에서는 iPhone과 중급 Android에서 캐시된 사진 토글 p95 150ms 이내, 1600px 저장 p95 1초 이내라는 기존 목표와 baseline을 같이 측정한다. 각 기기에서 준비/워밍업을 분리하고 같은 사진으로 30회 이상 측정하여 p50/p95·최대 메모리·입력 지연을 기록한다. 목표를 결과에 맞춰 낮추지 않으며, 초과하면 최적화 또는 출시 보류 사유로 남긴다. P3/sRGB, 반투명 가장자리, 방향/crop, 화면 밀도, JPEG 85, 미리보기/저장 일치와 실제 사용자 촬영 사진도 F에 포함한다.

## 2026-10-26 옅은 색의 공간 보정과 미리보기 일치

이번 변경은 `PRD.md` FR-PHOTO-002의 색 강조 품질을 개선한다. 새 라이브러리·네이티브 설정·서버 변경은 없다.

### 확인한 문제

- 기존 분류기는 각 픽셀을 독립적으로 판정했다. 회색 표면의 약한 색 잡음과 같은 색 표면의 옅은 반사광에 주변 색의 근거를 사용할 수 없었다.
- 옅은 색에서 흑백 배경과 강조 색의 밝기가 달라, 낮은 채도의 작은 변화가 밝고 어두운 얼룩으로 확대됐다. 공개 `china` 사진의 하늘에서 확인했다.
- 미리보기는 화면 크기로 그린 이미지에 필터를 걸고, 저장은 사진 해상도에서 처리했다. 주변 픽셀을 참고하는 필터는 이렇게 서로 다른 해상도에서 적용하면 같은 결과를 보장할 수 없다.

### 최종 처리

1. 기존 색상군 분류와 흰색·회색·깊은 그림자 제외는 유지한다.
2. 채도가 낮아 확신하기 어려운 픽셀에만 상하좌우 1픽셀의 색 유사도·불투명도를 참고한다. 중심 픽셀의 가중치를 더 크게 두고 보정 폭을 최대 0.20으로 제한한다. 색 자체를 주변 RGB로 대체하지 않는다.
3. 완전히 제외된 색과 선명한 작은 색 영역은 보정하지 않는다. 반투명 경계 밖의 투명 픽셀은 투표하지 않고, 사진 경계는 clamp로 처리한다.
4. 옅은 표면의 명암은 같은 흑백 기준 톤에 맞춰 강조 확률 변화가 밝기 얼룩을 만들지 않도록 한다. 채도 0.18~0.35 구간에서 이 보정을 부드럽게 줄이며, 선명한 색의 기존 강조를 유지한다.
5. `renderColorIsolationImage.ts`에서 사진 해상도로 한 번 처리한 스냅샷을 미리보기에서 축소해 표시한다. 저장도 같은 함수를 사용한다. 표시 크기만 바뀌면 필터를 다시 실행하지 않는다.

처음 검토한 모든 부분 선택 픽셀의 주변 평균은 짙은 와인 잎·초록 잎의 일부를 줄여 채택하지 않았다. 최종 버전은 낮은 채도의 불확실성에만 적용한다. 사물 전체를 인식하거나, 사진 속 색을 오늘 색으로 칠하는 기능은 아니다.

렌더링은 설치된 Skia 2.6.2의 `makeShaderWithChildren`과 원본 이미지 shader를 사용한다. 화면 밀도 영향을 받는 RuntimeShader 이미지 필터 대신 같은 사진 픽셀 좌표에서 평가하도록 통일했다. 참고: [Skia 이미지 필터의 픽셀 밀도 안내](https://wcandillon.github.io/react-native-skia/v2/docs/image-filters/runtime-shader/).

### 검증과 한계

- 실제 production SkSL을 CanvasKit에서 실행해 약한 잡음 억제, 반사광 보정, 색 번짐 방지, 작은 선명한 색 보존, 투명 경계, 옅은 표면의 명암 일관성을 검증했다. 수정 전 공간 보정 2개·명암 1개 테스트가 실패하고 수정 후 통과했다.
- 앱 테스트 88개 스위트/439개, 타입 검사·린트, 평가 도구 테스트 10개, 설정 테스트 21개를 확인했다. 미리보기·저장 리소스 해제와 파일 저장 실패 시 원본 보존도 포함한다.
- 공개 사진 6장/11개 색 조합의 기존 부분 영역 평가를 수정 전 `debc4ec`와 비교했다. 주황 우주복의 오검출 픽셀은 810→754, IoU는 0.8061→0.8131이었다. 보라·빨강·와인·분홍·꽃의 주황·민트와 목표색 없는 두 사례의 이진 마스크 집계는 동일했다.
- 하늘 IoU는 0.896949→0.896312, 초록 잎은 0.310313→0.310771로 사실상 비슷한 수준이다. 하늘에서는 정답 영역 확대보다 밝기 얼룩 감소가 주된 개선이다. 모든 색의 인식 정확도가 상승했다고 해석하지 않는다.
- 비교 결과는 `/tmp/mycolorlog-spatial-before`, `/tmp/mycolorlog-spatial-final-tone`에 생성했다. 사진 SHA-256과 기존 평가 영역·기준은 변경하지 않았다. 이 자료는 이미 개발에 사용한 사진이며 독립 검증 자료가 아니다. 정식 출시 판정은 계속 `not-evaluated`다.
- 네이티브 빌드·실기기 검증은 이번에 실행하지 않는다. 원본 해상도 미리보기의 최대 메모리·처리 시간, 1600px 저장, 화면 밀도·P3·JPEG 저장 차이와 실제 촬영 사진은 마지막 iPhone/Android QA에서 확인해야 한다. 저장은 JPEG이므로 미리보기와 압축 후 값이 완전히 같다는 뜻은 아니다.
