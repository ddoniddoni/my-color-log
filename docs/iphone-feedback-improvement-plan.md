# iPhone 실사용 피드백 개선 계획

- 작성일: 2026-10-22
- 상태: A 구현·자동 검증 기록 반영 / 이후 단계와 실기기·정식 평가는 대기
- 기준: `develop`의 `cb63022`, 사용자가 iPhone에서 확인한 5개 문제

헤더와 테마를 먼저 정리하고, 미션 색상 구성을 확정한 뒤 그 색상을 실제 사진에서 잘 찾도록 개선한다. **사용자 제보 1·4번 → 2번 → 3번 → 5번** 순서로 진행한다. 1·4번은 같은 헤더 컴포넌트를 수정하므로 하나의 작업으로 묶는다.

이 문서는 실행 계획과 진행 기록이다. 체크된 항목과 마지막 실행 기록만 완료 근거로 사용한다. 아직 실행하지 않은 단계의 성능 수치는 목표안이며 측정 결과가 아니다.

## 3. A — 헤더 통일과 아이콘 정리

관련 요구사항: PRD §9 정보 구조, S05/S06/S09/S13/S16/S18, §21 접근성. DESIGN §5 간격, §8 아이콘, §11 화면 레이아웃.

### 화면 규칙

공통 `AppHeader`를 만들고 탭 최상위는 **화면 제목 좌측 정렬 + 필요한 우측 동작**으로 통일한다. 기존 스케치 느낌은 본문과 일러스트에 유지한다.

| 화면 | 헤더 제목 | 우측 동작 | 본문에 배치할 정보 |
| --- | --- | --- | --- |
| 오늘 | 오늘 | 설정 → 기존 내 정보의 설정 목록 | 날짜, 시간대, 오늘의 색 |
| 친구방 목록 | 친구방 | 설정 → 내 정보 | 참여 방 수, 만들기·참여 CTA |
| 다이어리 | 다이어리 | 설정 → 내 정보 | 월 이동·날짜 선택 |
| 내 정보 | 내 정보 | 없음 | 프로필과 기존 설정 목록 |
| 오늘의 색 공개 | 오늘과 같은 상단 규격 | 진행 중에는 화면 이탈 동작 생략 | 날짜·공개 안내·컬러 링 |
| 방 상세·기록 등 하위 화면 | 뒤로 + 해당 제목 | 실제 제공하는 관리 동작만 | 멤버 수·날짜 등 화면 정보 |

설정 아이콘은 실제 `Pressable`로 연결하고 접근성 이름을 `설정 열기`로 제공한다. 내 정보의 햄버거와 장식용 톱니바퀴는 제거한다. 내 정보가 이미 설정 목록을 포함하므로 새 햄버거 메뉴나 별도 설정 체계는 만들지 않는다.

## 4. B — 오늘 탭의 라이트/다크 연동

관련 요구사항: PRD S04/S05/S06/S18/S19, §21 접근성. 기존 `ThemeProvider`와 내 정보의 `화면 테마` 기능을 기준으로 수정한다.

### 재현과 수정

- [ ] `내 정보 → 화면 테마 → 어둡게 → 오늘`, `밝게 → 오늘`, `시스템 설정 → OS 모드 변경`을 각각 재현한다. 사용자가 본 실패 경로를 기록한다.
- [ ] 공개 전·공개 후·사진 0/1/9장·오프라인·조회 오류에서 `preference`와 `resolvedTheme`, 실제 화면 색의 일치 여부를 확인한다. 계정·사진 정보를 로그로 남기지 않는다.
- [ ] `userInterfaceStyle`을 `automatic`으로 정리한다. Android appearance 지원에 필요한 `expo-system-ui`를 현재 Expo SDK에 맞춰 `npx expo install expo-system-ui`로 추가한다. 공식 설정 근거: [Expo Color themes](https://docs.expo.dev/develop/user-interface/color-themes/).
- [ ] 수동 선택은 시스템 설정보다 우선하고 `system`일 때만 OS 변경을 따른다. 테마를 바꾸기 위해 오늘 화면을 강제 remount하거나 미션 공개 이력을 초기화하지 않는다.
- [ ] 이미 테마를 구독하는 컴포넌트를 중복 Provider로 감싸지 않는다. 재현 결과에 따라 정적 색·스타일 캐시·네이티브 배경·화면 전환 배경의 누락 지점만 수정한다.
- [ ] 저장된 설정을 읽는 동안 밝은 화면이 순간 노출되는지, 초기 저장값 로딩이 새 선택을 덮어쓰는지 확인한다. 저장 실패 시 선택 표시와 재시작 결과가 모순되지 않도록 처리한다.
- [ ] 네이티브 설정이 바뀌므로 iOS·Android development build를 다시 만든다. Metro 새로고침만으로 검증을 끝내지 않는다. 로컬 Personal Team 서명 설정과 베타·운영 variant 구분은 보존한다.

주요 파일: `app.json`, `app.config.ts`, `package.json`, `package-lock.json`, `src/design/ThemeProvider.tsx`, `src/design/themePreference.ts`, `src/features/profile/components/ThemeSettingsModal.tsx`, 오늘 관련 컴포넌트, `app/_layout.tsx`, `scripts/__tests__/iosBuildConfiguration.test.cjs`.

### 완료 기준

- [ ] 수동 밝게/어둡게 선택이 네 탭과 색 공개·모달에 즉시 반영된다.
- [ ] `system` 상태에서 OS 변경·백그라운드 복귀가 반영되고 수동 선택은 OS 변경에 영향받지 않는다.
- [ ] 앱 종료·재실행 후 선택이 유지된다. AsyncStorage 읽기·쓰기 실패의 복구 동작을 테스트한다.
- [ ] 상태 표시줄·탭 바·헤더·빈 모자이크·버튼·오류 안내가 두 테마에서 읽힌다.
- [ ] 테마가 바뀌어도 미션 대표색과 사진 자체의 색은 바뀌지 않는다.

DB 변경: 없음. 네이티브 모듈·설정 변경은 두 플랫폼 빌드 검증이 필요하다.

> 체크된 로직 항목은 컴포넌트/단위 테스트 기준이다. 네 탭 이동, OS appearance 변경·복귀, 강제 종료 후 실제 기기 재실행 및 시각 대조는 실기기 QA에서 확인한다. 네이티브 시작 화면은 OS 모드를 따르고, 저장된 수동 테마는 JS 설정 로딩 후 첫 앱 화면부터 적용한다.

### 작업

- [ ] 운영의 현재 활성 색상·RPC 정의를 읽기 전용으로 확인한다. migration의 초기값과 현재 데이터가 다르면 실제 사용 이력을 먼저 정리한다.
- [ ] 10색을 밝은/어두운 배경의 링·디스크·칩·달력에 배치해 비교한다. 특히 레드/와인/핑크/퍼플, 민트/그린, 스카이/블루가 충분히 구분되는지 확인한다.
- [ ] Oklab 등의 지각 색 공간으로 색 간 거리를 보조 측정하고 실제 표시와 함께 판단한다. 단일 거리 수치를 사진 인식 임계값으로 재사용하지 않는다.
- [ ] 신규 색마다 한국어·영어 이름, 대표색, tint/shade, `on_color_hex`, 관찰 문구를 준비한다. 와인은 어두운 모드에서도 경계가 보이도록 중립 테두리를 사용한다.
- [ ] 새 timestamp migration으로 `cl_color_palette`에 새 ID/slug를 추가하고 제외 후보는 `is_active=false`로만 처리한다. 이미 참조된 색의 HEX·이름·ID를 덮어쓰거나 삭제하지 않는다.
- [ ] 기존 `cl_daily_missions`와 방 미션은 그대로 둔다. 변경 후 처음 생성되는 미션부터 새 활성 목록을 사용한다. 이미 정해진 오늘 색을 강제로 교체하지 않는다.
- [ ] `cl_get_mission_reveal_palette`의 결과가 항상 **중복 없는 10개이며 실제 미션 색을 포함**하는지 검증한다. 과거의 비활성 색이 당일 결과인 경우도 포함한다.
- [ ] 링의 색 순서와 포인터가 실제 서버 결과에 정확히 맞는지 확인한다. 순서를 바꾸면 target index·회전 계산도 같은 데이터로 계산한다. 슬롯 수와 API 형태는 유지한다.
- [ ] 최근/예시 날짜의 선정 분포를 검토한다. 이번 작업에서 별도 재추첨이나 조회 순서에 의존하는 연속 중복 방지 정책은 추가하지 않는다.
- [ ] [색 공개 문서](color-reveal.md)와 팔레트 계약 테스트를 갱신한다.

주요 파일: 새 `supabase/migrations/<timestamp>_refresh_cl_mission_palette.sql`, 새 `supabase/tests/mission_palette_contract.sql`, `src/features/missions/model/dailyMission.ts`, `missionRevealWheel.ts`, `src/features/missions/api/missionRepository.ts`, `MissionReveal.tsx`와 관련 테스트. 기존 migration은 수정하지 않는다.

### DB 적용·복구 규칙

[공유 Supabase 운영 규칙](shared-supabase.md)을 따른다. 폐기 가능한 로컬 DB에서 기존 설치 → 신규 migration과 새 설치 → 신규 migration을 검증한다. 공유 서버에는 검토한 새 migration 파일만 명시적으로 적용하고 `cl_private.schema_migrations`에 기록한다. `db push`, 공유 서버 `db reset`, 최초 설치 재실행은 사용하지 않는다. [Supabase migration 문서](https://supabase.com/docs/guides/deployment/database-migrations)는 이력 관리 참고 자료다.

되돌릴 때도 새 migration으로 활성 목록을 복구한다. 이미 생성된 미션·사진·색상 행은 보존한다. 기존 설치/검증 스크립트에 색상 10개 가정이 있으면 총 행 수와 활성 행 수를 구분하도록 점검한다.

### 완료 기준

- [ ] 신규 팔레트에서 보라·와인이 실제 미션 후보와 공개 화면에 포함된다.
- [ ] 동일 날짜 재실행·동시 요청·같은 방에서 동일 미션이 유지된다.
- [ ] 기존 다이어리와 방 기록의 색·이름·참조 ID가 변하지 않는다.
- [ ] 비활성 과거 색을 포함한 10칸 공개가 현재 앱 파서와 호환된다. 기존 클라이언트에도 같은 응답 형태를 유지한다.
- [ ] 새 색의 텍스트 대비, 모션 감소, 두 테마 표시를 확인한다. 기존 약 2.1초 공개 연출과 결과 유지 동작을 보존한다.
- [ ] `cl_` 외 테이블·Auth·다른 앱 설정을 변경하지 않는다. RLS 및 RPC 권한을 약화하지 않는다.

> 구현/DB 계약 항목은 로컬 검증 기준이다. 공유 서버에는 아직 적용하지 않았고, 두 테마 시각 비교는 디자인 검토 이미지와 컴포넌트 테스트로 확인했다. 실제 기기 렌더링·모션 검증은 전체 수정 후 F에서 진행한다.

## 6. D — 실제 사진 평가와 기술 선택

관련 요구사항: FR-PHOTO-002/005/006, PRD §20 성능, §29.7 저장 비차단. 목표는 **오늘의 색 영역을 더 잘 남기고, 관계없는 색이 남는 현상을 줄이는 것**이다.

### 현재 방식에서 검증할 가설

- 정규화 RGB 거리의 고정 임계값이 모든 색상군에 동일한 시각적 허용 범위를 주지 않을 수 있다.
- 어두운 와인·저채도 보라가 채도/밝기 억제로 빠질 수 있다. 임계값을 넓히면 피부·나무·조명에 물든 흰색이 함께 살아날 수 있다.
- 현 방식은 명도와 채도를 제거해 색상 방향을 비교하므로 레드와 와인처럼 명도·채도가 의미 있는 차이를 잃는다. 반대로 명도를 너무 엄격히 비교하면 같은 물체의 그림자가 빠진다.
- 입력 이미지와 미리보기/오프스크린 저장의 색 공간, 샘플링, 알파 처리 차이가 결과를 바꿀 수 있다. 현재 알파 해제/복원과 `layout(color)` 처리는 이미 있으므로 누락으로 단정하지 않는다.

### 조사한 후보와 권장 방향

| 후보 | 용도와 판단 | 적용 전 확인 |
| --- | --- | --- |
| 기존 React Native Skia 2.6.2 + 색상군별 HSV/색상 각도 범위 | 기존 렌더링 구조에서 구현할 첫 비교군. hue 경계·채도·밝기 허용 범위를 색별로 조절 | 미세한 유사색 구분과 저조도 성능 |
| 기존 Skia + Oklab/OKLCH 기반 거리·색상군 범위 | 지각에 가까운 명도·채도·색상 차이를 반영하는 우선 비교군 | 밝기 가중치, 무채색 근처의 불안정한 hue, 처리 비용 |
| OpenCV + `react-native-fast-opencv` | HSV `inRange`와 마스크 후처리를 비교하는 대안. D에서는 먼저 오프라인 평가하고 앱 도입은 측정 결과로 결정 | Expo 57/RN 0.86.3 호환, C++ 바이너리 증가, 스레드·메모리, iOS/Android 결과 차이 |
| Color.js | 팔레트의 색 공간 변환·색차 계산과 테스트 기준값 생성에 유용 | 필요 시 개발 도구로 제한. 앱 사진 전체 픽셀을 JS 루프로 처리하는 용도로 쓰지 않음 |

근거와 해석:

- [React Native Skia v2 RuntimeShader](https://wcandillon.github.io/react-native-skia/v2/docs/image-filters/runtime-shader/)는 사용자 정의 이미지 필터를 제공하며 픽셀 밀도 처리를 별도로 확인하도록 안내한다. 이미 설치된 기능이므로 우선 활용하는 것이 이 프로젝트의 변경 범위를 줄인다는 판단이다.
- [Skia SkSL 색 공간·알파 문서](https://skia.org/docs/user/sksl/)를 기준으로 작업 색 공간과 linear sRGB 변환을 검증한다. 미리보기와 저장을 같은 색 기준으로 비교해야 한다.
- [Oklab 원저자 설명](https://bottosson.github.io/posts/oklab/)은 명도·채도·색상 처리를 위한 지각 색 공간을 제시한다. 이 앱 사진에서 정확도가 개선된다는 것은 아직 검증할 가설이다.
- [OpenCV HSV 범위 검출](https://docs.opencv.org/4.x/da/d97/tutorial_threshold_inRange.html), [마스크 형태 연산](https://docs.opencv.org/4.x/d9/d61/tutorial_py_morphological_ops.html)은 범위 검출과 작은 잡음·구멍 정리의 비교 기준이다. 작은 색 물체까지 지우지 않는지 함께 측정한다.
- [Fast OpenCV 소개](https://lukaszkurantdev.github.io/react-native-fast-opencv/)와 [설치 문서](https://lukaszkurantdev.github.io/react-native-fast-opencv/installation)는 독립 사용, 네이티브 바이너리, 동기 호출의 스레드 분리 필요성을 설명한다. 현재 문서는 플랫폼별 OpenCV 버전도 다르다고 안내한다. 도입 시 해당 버전의 함수 지원·라이선스·빌드를 다시 확인한다.
- [Color.js 색차 문서](https://colorjs.io/docs/color-difference)는 여러 ΔE 계산을 제공한다. 평가 도구의 알고리즘과 스케일을 명시해 서로 다른 거리 수치를 혼용하지 않는다.

선정 원칙: 같은 사진에서 현 방식, HSV 계열, Oklab 계열을 비교한다. OpenCV의 후처리가 유의미한 이득을 보일 때 네이티브 도입까지 검토한다. 전체 카메라 라이브러리 교체나 외부 AI 서버 전송은 기본 계획에 포함하지 않는다.

### 평가 자료와 기준

- [ ] 목표 40장 이상: 후보 10색마다 자연광·실내 따뜻한 조명·그림자·복잡한 배경을 포함한다. 보라·와인과 비슷한 색이 함께 있는 장면, 색이 없는 흰색·회색 배경을 별도 포함한다.
- [ ] 직접 촬영하거나 사용 권한이 있는 사진만 사용한다. 사용자 사진은 허락 없이 저장소에 추가하거나 외부 서비스로 보내지 않는다. EXIF·위치정보를 제거한다.
- [ ] 사람이 오늘 색 영역을 표시한 기준 마스크를 만든다. 레드/와인처럼 경계가 애매한 사례는 원하는 동작을 먼저 합의하고 경계 픽셀을 평가에서 별도 처리한다.
- [ ] 같은 장면의 변형이 평가 양쪽에 들어가지 않도록 조정용/검증용 자료를 분리한다. 후보별 결과와 실패 예시를 같은 순서로 비교한다.
- [ ] 색 영역 정확도는 precision(남긴 영역의 정확성), recall(찾아낸 비율), IoU(영역 겹침)를 색상군별로 기록한다. 마스크 판정 경계는 고정하고 배경 비중이 높은 전체 픽셀 정확도로 대체하지 않는다.
- [ ] **초기 채택 기준안:** 검증 자료 macro IoU가 현 방식보다 0.05 이상 개선, 색상군별 precision/recall 하락이 0.03 이내, 보라·와인의 누락 감소. 목표색 없는 사진에서 잘못 남긴 면적 비율도 현 방식 이하. D에서 기준을 확정한 뒤 최종 검증 결과를 보고 낮추지 않는다.
- [ ] iPhone과 중급 Android에서 미리보기 준비 시간·저장 변환 시간 p50/p95·최대 메모리를 측정한다. 초기 목표는 캐시된 사진의 토글 반영 p95 150ms 이내, 현재 앱의 최대 처리 해상도 저장 p95 1초 이내이며 실제 baseline과 함께 D에서 확정한다. JS 입력 정지·강제 종료는 허용하지 않는다.

> D 파일럿 범위: 공개 사진 6장 / 장면-목표 조합 11개와 합성 10색을 비교했다. 에이전트가 표시한 일부 영역이며 사람 검수 전체 마스크가 아니다. 위 체크는 도구·파일럿에 한정되고 40장 정확도 기준은 미충족이다. 결과를 확인한 장면을 E 튜닝에 쓰면 최종 holdout은 새 장면으로 확보한다. 성능 측정은 사용자 지시에 따라 F에서 한다.

산출물: 평가용 fixture와 실행 도구, 후보별 비교 표, 라이선스/호환성 기록, 선택 근거. 개인정보 사진·생성된 대용량 결과물은 커밋하지 않는다. 기존 CanvasKit 합성 테스트도 유지한다. D에서는 제품 기본 동작을 바꾸지 않는다.

## 7. E — 색상 인식 개선 반영

### 작업

- [ ] D에서 선정한 계산을 `colorIsolation` 도메인 모듈에 구현한다. 목표색 판별 마스크와 배경 흑백화·채도 강조를 구분해 각각 검증한다.
- [ ] 모든 색에 동일 수치를 강제하지 않고 색상군별 허용 범위를 둔다. 단일 대표 HEX와의 엄격한 일치보다 조명에 따른 변화 폭을 평가한다. 와인과 레드의 구분은 D의 기준 마스크를 따른다.
- [ ] sRGB/Display P3 입력, 선형화, 알파, crop/회전, 화면 축소의 영향을 확인한다. 필요 시 공통 색 공간으로 정규화하되 사진의 본래 색을 목표색으로 칠하지 않는다.
- [ ] 필요성이 확인된 경우에만 마스크 후처리를 추가한다. 작은 물체·얇은 가장자리의 색이 유지되고 색 테두리나 번짐이 생기지 않게 한다.
- [ ] `ColorIsolationSkiaPreview`와 저장 repository가 같은 알고리즘·파라미터를 사용하도록 한다. GPU 자원·파일은 실패 경로에서도 정리한다.
- [ ] 원본/효과 비교가 가능한 검토 화면을 유지한다. 수동 범위 조절·사진 터치로 색 선택은 자동 개선 후에도 남는 실패 사례가 있을 때 별도 후속 작업으로 판단한다.
- [ ] 처리 실패 시 원본 보존과 효과를 끈 저장 경로를 제공한다. 색 검출 실패나 목표 영역이 작다는 이유로 촬영·저장을 막지 않는다.
- [ ] 이미 저장된 사진은 자동 재처리하지 않는다. `colorIsolationApplied`의 중복 적용 방지와 기존 드래프트 복구를 유지한다. 새 옵션을 영속화한다면 optional/versioned 필드와 이전 큐 파서를 함께 검증한다.

현재 저장 처리는 효과 파일 쓰기와 큐 갱신 후 이전 로컬 파일을 정리한다. 재시도나 적용 완료 드래프트에서 원본으로 되돌릴 수 있다고 가정하지 않는다. 조절·재편집을 추가하려면 원본 URI의 별도 보존, 업로드 성공 전 보존 정책, 취소·복구 시 파일 정리부터 설계해야 한다. 이번 기본 범위는 판별 개선과 실패 시 안전한 저장이다.
