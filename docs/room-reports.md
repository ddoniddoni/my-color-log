# 친구방 신고 접수

요구사항: PRD `FR-ROOM-011`. 구현 범위는 신고 등록과 서버 접수다.

## 앱 동작

- 친구방 오늘·과거 기록의 다른 멤버 사진 상세에서 **사진 신고**를 누른다.
- **친구방 관리 → 멤버 신고**에서 대상 멤버를 선택할 수도 있다. 일반 멤버도 방장을 신고할 수 있다.
- 팝업에서 사유를 선택하고 **신고 등록**을 누른다. 상세 내용은 최대 500자이며 기타 사유에서는 필수다.
- 기존 사진·관리 팝업 안에서 신고 화면으로 전환한다. iOS native Modal을 겹쳐 열지 않는다. 취소하면 원래 화면으로 돌아간다.
- 등록 중 중복 터치와 팝업 닫기를 막는다. 20초 응답 제한을 두고, 실패하면 입력을 유지한다. 자동 재시도·오프라인 큐에는 넣지 않는다.
- 서버 접수 응답을 확인한 뒤 완료를 표시한다. 응답이 유실되어 다시 누르더라도 동일 접수 번호로 수렴한다.
- 한국어·영어 및 라이트·다크 테마를 지원한다. 사유의 선택 상태를 접근성 정보로 제공하고, 스크롤과 키보드 회피를 사용한다.

## 서버와 권한

- `public.cl_submit_room_report`는 invoker 공개 RPC이고, 권한을 검사하는 구현은 `cl_private.submit_room_report`에 둔다.
- 영구 계정의 유효한 Auth 세션을 확인한다. 신고자·신고 대상 소유자·접수 시각·초기 `pending` 상태를 서버에서 결정한다.
- 멤버 신고는 같은 방의 활성 멤버만 가능하다. 사진 신고에는 방 날짜, 가입일, 활성 멤버십, 공유 연결, 일치하는 방 미션을 확인한다. 본인·다른 방·탈퇴·공유 해제·방 종료 대상은 거절한다.
- `cl_room_reports`는 RLS를 활성화하고 일반 앱 계정의 직접 읽기·쓰기 권한을 주지 않는다. 접수 결과에는 ID와 중복 여부만 포함한다.
- 같은 신고자·방·사진, 또는 같은 신고자·방·멤버 조합은 한 건이다. 기존 사유를 덮어쓰지 않는다. 상태가 변경되어도 현재 중복 기준은 유지된다.
- 신고자별 잠금으로 동시 요청을 직렬화하여 최근 24시간 새 신고 20건 제한을 검사한다. 기존 신고의 재확인은 새 한도를 차지하지 않는다.
- 사진·캡션을 복사하지 않는다. 신고가 사진 숨김·삭제·멤버 차단이나 알림 발송을 자동 실행하지 않는다.

## 운영자가 확인하는 곳

현재는 **Supabase Dashboard → 해당 프로젝트 → Table Editor → `cl_room_reports`**에서 확인한다. `status = pending`으로 필터하고 `created_at` 최신순으로 정렬한다.

| 필드 | 의미 |
| --- | --- |
| `target_type` | `photo`: 사진 신고 / `member`: 멤버 신고 |
| `reporter_id`, `reported_user_id` | 신고자·대상자의 Color Log 프로필 ID |
| `room_id`, `photo_id` | 대상 친구방·사진 참조. 멤버 신고의 사진 ID는 비어 있음 |
| `reason`, `details` | 선택한 사유와 입력한 상세 내용 |
| `status`, `created_at` | 처리 상태와 UTC 접수 시각 |

사유 코드는 `inappropriate`(성적·불쾌한 콘텐츠), `harassment`(괴롭힘·혐오), `privacy`(개인정보), `illegal`(불법·권리 침해), `spam`(스팸·광고), `other`(기타)다.

별도 운영자 화면과 신규 접수 알림은 아직 없다. `pending/reviewing/resolved/dismissed`는 상태 저장값이며, 값을 바꿔도 제재나 이용자 안내가 실행되지는 않는다. 관리자 권한·service role 키를 앱이나 공개 웹페이지에 넣지 않는다.

## 보관과 삭제

신고자 또는 대상자의 Color Log 프로필, 관련 방, 대상 사진이 실제 삭제되면 연결된 신고도 함께 삭제된다. 방 나가기·방 종료는 논리적인 상태 변경이므로 기존 신고는 남는다. 증거 사진 별도 보존과 처리 완료 후 정기 삭제는 구현하지 않았다. 출시 전 보관 기한과 운영 절차를 확정하고 공개 개인정보 페이지에도 반영한다. 저장소의 개인정보 처리방침 초안에는 새 처리 항목을 반영했다.

## 배포

2026-10-25 `.env` 대상 공유 서버에 `20261024174731_add_cl_room_reports.sql` 한 파일을 적용했다. 기존 객체 328개의 테이블 정의·권한, 함수, 정책, 사용자 트리거를 적용 전후 비교했으며 동일했다. 공개 테이블 1개와 공개·비공개 접수 함수 각 1개를 추가했다.

새 환경에서는 최초 `cl_` namespace 설치 후 아래 파일만 별도로 적용한다. 팔레트·푸시·재가입 migration과 독립적이다. 공유 프로젝트에서 `db push`·`db reset`·과거 migration 일괄 실행을 사용하지 않는다.

```sh
npx --yes supabase@2.121.0 db query --linked --project-ref <.env의-대상-project-ref> --yes --file supabase/migrations/20261024174731_add_cl_room_reports.sql
```

## 검증

```sh
npm test -- --runInBand src/features/reports
npm run typecheck
npm run lint
npm run test:db:room-reports
```

DB 계약은 **폐기 가능한 로컬 DB**에서만 실행한다. 트랜잭션 fixture를 만들고 `authenticated`/`anon` 역할로 실제 RPC와 직접 테이블 접근을 검사한 뒤 롤백한다. 공유 운영 서버에는 계약 fixture를 실행하지 않는다.

- 앱 테스트: 사유·500자 검증, 서버 DTO, 실패 입력 유지·재시도, 중복 터치, 응답 전 완료 표시 차단, 사진 선택 대상, 본인 버튼 미노출, 일반 멤버의 방장 신고.
- SQL 계약: 익명·세션 해지·권한·날짜·본인·외부 방·탈퇴·공유 해제·방 종료 차단, 중복, 한도, 삭제 연쇄, 사진 보존.
- 격리 PostgreSQL 18.4에서 독립 namespace 및 전체 migration 이력 설치에 SQL 계약 10개씩 통과. 최소 namespace + 신고 migration 설치도 통과했다.
- 별도 DB 세션 8개의 동일 대상 동시 접수는 1건으로 수렴했다. 20·21번째 요청 경합에서도 20건 한도를 유지했다.
- 로컬 Supabase 보안 Advisor: `No issues found`.
- 공유 서버의 실제 Auth + publishable key 세션으로 사진·멤버 접수, 4개 동시 재시도의 단일 저장, 운영자 조회, 일반 계정 읽기·직접 쓰기 차단, 본인·외부인·탈퇴·해지 세션 차단을 통과했다. 사진 메타데이터 보존도 확인했고 생성한 QA 계정·방·기록·신고를 정리했다. 사진 파일 업로드·열기는 이번 HTTP 검증 범위에 포함하지 않았다.
- 공유 서버 보안 Advisor 응답은 오류 등급 0건이며 신규 신고 객체 관련 진단은 없었다. 다른 기존 객체의 경고가 남아 있으므로 프로젝트 전체의 보안 검증 완료를 의미하지 않는다.
- `npm run check`: typecheck·lint, Jest 80 suites / 379 tests, 색 강조 도구 10개, 빌드 설정 검사 21개 통과. 네이티브 앱 빌드는 실행하지 않았다.
- React Doctor 0.9.18에서 새 파일을 포함해 `develop` 기준 변경 검사를 실행했다. 신규 진단 0건, 기존 진단 2건 유지, 점수 93으로 회귀가 없었다.

앱 빌드와 실기기 QA는 사용자 요청대로 마지막 통합 검증에 남긴다. 특히 iPhone·Android에서 팝업 전환, 키보드·큰 글씨, 뒤로 가기, 응답 지연·비행기 모드 재시도, 실제 신고 등록 후 운영자 확인을 점검한다.
